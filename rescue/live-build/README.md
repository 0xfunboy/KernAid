# Rescue image

This Debian 13 (`trixie`) live-build profile creates an amd64 hybrid ISO for legacy BIOS and UEFI. It starts XFCE and opens the local KernAid Desk web bundle in Chromium app mode. Host storage automount is denied for the live user. Each QEMU smoke test attaches a disposable target disk and byte-hashes it before and after boot to prove zero target writes.

Before SHA-256 is calculated, the build finalizes the immutable Phase 0 device layout declared in `rescue/image-layout/device-layout.v1.json`. It writes only MBR slot 3: type `0x83`, start LBA `33554432` (16 GiB), and `16777216` sectors (8 GiB). The ISO file is not padded or enlarged. Consequently the entry intentionally points beyond ISO EOF and describes where a `KERNAID_VAULT` can exist only after the ISO is written to media of at least 24 GiB; the supported capacity claim is 32 GB or larger. The release ISO itself never contains a formatted vault, a key, or provisioning code.

Debian isohybrid images have one narrowly allowed MBR overlap: bootable slot 1 type `0x00` is an image envelope that contains slot 2 type `0xEF`, the EFI System Partition. The finalizer accepts only that exact containment form; it rejects every other slot 1/2 overlap or ordering, any occupied slot 4, any conflicting slot 3, an ISO reaching the reserved vault start, and non-regular image files. Re-running finalization is idempotent only when slot 3 already contains the exact layout-v1 bytes. The QEMU smoke script runs the same verifier read-only before boot.

Build in a disposable Debian environment with `sudo just build-rescue`. The GitHub `rescue` workflow builds the image, waits for both the general and validated-target-selection serial markers in QEMU BIOS and UEFI, verifies zero target writes, and uploads the ISO, SHA-256 checksum, QEMU logs, and derived catalog entry.

The workflow keeps two intentionally separate boot attestations. The original `qemu-smoke.sh` boots the ISO as a virtual CD-ROM once per firmware and remains the evidence consumed by catalog v1. The additional root-only `qemu-usb-smoke.sh` copies that finalized ISO, without truncation, into the prefix of one sparse 32,000,000,000-byte raw medium under `/tmp`. It binds only p3 through a newly allocated offset/size-limited loop, provisions it as LUKS2 plus ext4 with the exact `KERNAID_VAULT` labels, creates the root-owned V1 marker/layout, and invokes the separately built host probe to initialize the encrypted journal sentinel and `DeviceIdentity`. Its random key and wrong-key fixture are mode 0600 files beneath `/dev/shm`; neither they, the provisioner, nor the probe are added to the ISO.

After the initialize lifecycle closes cleanly, the loop is detached and the same raw medium boots twice through QEMU `usb-storage` for each firmware. UEFI receives a fresh OVMF VARS copy on each boot, while the disposable observation target remains a separate writable virtio disk. Prefix, provisioned p3, and target hashes are checked after each boot and across the complete two-boot window. Only after that raw-byte window closes does the host reattach the exact p3 slice, prove wrong-key rejection without residue, and run the probe in verify mode. The verify mode authenticates the one journal sentinel and loads the same device identity; LUKS and filesystem UUIDs must also remain stable. Both successful managed lifecycles must shut down without a mount or mapper, and the final loop must be detached.

Each USB log therefore contains exactly one `KERNAID_QEMU_USB_ATTESTATION_V1` line and one catalog-v2-compatible `KERNAID_QEMU_USB_VAULT_ATTESTATION_V1` line. `p3_before_sha256` and `p3_after_sha256` describe the post-initialize raw bytes across the two QEMU boots. The later read-write ext4 verify mount is deliberately outside that hash window and receives its own `KERNAID_QEMU_USB_VAULT_RAW_SCOPE_V1` digest, because an ordinary clean ext4 mount may update filesystem metadata. CI feeds both firmware logs to the inactive catalog-v2 entry generator as a contract check; this does not add an image to the trusted catalog.

This evidence proves boot survival of host-initialized encrypted state on disposable QEMU media. It does **not** prove that the live guest unlocks or uses p3, and it makes no claim that a vault daemon, passphrase UI, recovery workflow, or in-guest secure-state integration exists.

The generated image is an engineering preview. An MBR partition entry beyond the end of the ISO is deliberate but unconventional and remains an engineering gate for ISO tooling and physical USB firmware. Secure Boot, Wi-Fi coverage, physical-machine compatibility, and production in-guest vault integration remain release gates.

The loopback Rescue API exposes `GET /api/rescue/installed-targets`, `POST /api/rescue/select-installed-target`, and `POST /api/rescue/inspect-installed-target`. Desk drives them as an explicit scan → select → read-only inspect sequence; inspection accepts exactly the selected `scanFingerprint` and `targetId`. Identifiers use a random root-only key created in `/run` for the current boot, so separate one-shot helper instances share one identity epoch and every reboot invalidates it. Each operation re-scans before accepting an identifier, and a completed inspection re-scans again after cleanup. The scan collector runs one fixed, bounded `lsblk` metadata command, returns only normalized topology and boot-ephemeral identifiers, and excludes mounted/live-image disks. Repeated or incoherent kernel `MAJ:MIN` identities and shared/N:M topology make every involved disk non-selectable.

Desk accepts an inspection only when its exact schema, read-only/no-replay policy, claims, OS family, source reference, scan fingerprint, and target identifier remain cross-bound to the current selection. It then creates one SessionDriver evidence record containing only the bounded normalized Linux or Windows corpus, its versioned collector identity, and a fixed corpus-derived summary. Rescue-runtime inventory is used only for the visible live-environment status and the opaque session target fingerprint; it is never mixed into the installed-system diagnostic corpus. The deterministic provider requires that single corpus record and rejects duplicate, mixed, legacy selection-only, wrongly scoped, wrongly typed, or non-canonical evidence. Refresh, retarget, stale asynchronous responses, identity mismatch, and failed diagnosis revalidation invalidate the prepared inspection/session; target-identity failures also invalidate scan and selection. A performed mount without verified cleanup blocks further inspection until Rescue is restarted. Typed encrypted, Apple-filesystem, complex-storage, and unsupported-filesystem results remain explicit unsupported outcomes and never trigger unlock or activation.

The HTTP/UI process remains a `DynamicUser` with `NoNewPrivileges` and no mount capability. It can send only a fixed operation plus the two opaque identifiers over a mode-0660 Unix socket owned by the dedicated `kernaid-inspect` group. `Accept=yes` creates one root service instance, cgroup, and private mount/network namespace for each connection. Each instance has a 20-second systemd runtime limit, a two-second stop limit, `KillMode=control-group`, and handles exactly one frame before exiting; the kernel still cannot guarantee prompt termination of a task stuck in uninterruptible D-state, so hostile-filesystem kernel hangs remain an explicit physical/VM test gate. The helper resolves the exact kernel device itself, opens one direct devtmpfs block node read-only with no symlink following, verifies `st_rdev`, and mounts `/proc/self/fd/N`; neither an HTTP caller nor the UI can provide a command, device path, filesystem, mount option, or content path.

Offline inspection v1 allows only a leaf ext4 filesystem or a leaf NTFS filesystem directly on a disk. ext4 uses kernel flags `ro,nodev,nosuid,noexec,nosymfollow` plus `noload`. The kernel `ntfs3` driver does not implement `norecover`: KernAid mounts it exclusively with those read-only kernel flags, no filesystem-specific option, and never `force`; mount verification rejects a reported `force` super-option. On an `MS_RDONLY` ntfs3 mount the driver does not apply log replay, but KernAid does not classify or validate the volume's clean, dirty, hibernated, or scheduled-check state. The result therefore labels NTFS volume state `unqualified` and returns only static presence markers as `observed-untrusted`. The helper never follows fstab, executes or chroots into target content, launches a mount helper, removes a hibernation file, unlocks encryption, or activates storage. LUKS, BitLocker, APFS/HFS, LVM, mdraid, Btrfs, XFS, F2FS, nested mappings, conflicting OS hints, and ambiguous device identities return typed fail-closed errors. Content reads use a static path allowlist, directory file descriptors, `O_NOFOLLOW`, regular-file checks, incremental directory caps, and byte/file/response/deadline limits. Results contain a bounded normalized Linux or Windows corpus classified as `observed-untrusted`; raw registry hives, machine IDs, fstab sources, account names, device identifiers, commands, paths, stdout, and stderr are not returned.

Success is reported only after a normal (never forced or lazy) unmount, mount-table postcondition, unchanged open-device identity, and an identical post-cleanup target resolution. Every response is followed by one-shot service/cgroup exit, so a cleanup failure cannot reuse that mount namespace. Claims distinguish mount attempted/performed/cleaned, content inspected, and installation confirmed; they always state that auto-unlock, mutation, diagnosis, and repair were not performed. This is filesystem evidence capture, not a diagnosis or repair handler.

The BIOS and UEFI QEMU smoke path opts in explicitly through a QEMU-only fw_cfg marker, so ordinary Rescue boots never auto-inspect a customer target. It inspects a deterministic ext4 installed-Linux fixture marked `needs_recovery` and two deterministic NTFS installed-Windows fixtures, one cloned and altered by `ntfsfix`. Both NTFS fixtures must be accepted by the shipping kernel's ntfs3 driver exclusively read-only without `force`; their volume state remains explicitly unqualified. The smoke path byte-hashes all three raw images before and after the complete boot. Readiness requires normalized static corpora, exact no-replay/no-force policies, verified cleanup, and identical raw hashes. If that kernel rejects the altered NTFS fixture, the image qualification fails instead of weakening the policy or overstating support. Physical-machine coverage remains a release gate.

Rescue Observe authorization requires the existing request fields plus exactly `"rescueTarget":{"scanFingerprint":"…","targetId":"…"}`. The server performs selection A, runtime inventory, then selection B; both complete selection responses must be identical. Its `targetFingerprint` is SHA-256 over the UTF-8, NUL-delimited sequence `kernaid-rescue-observe-target-v1`, runtime inventory fingerprint, scan fingerprint, target ID, and the complete candidate encoded as JSON with recursively lexical keys, ASCII escaping, and no whitespace. Missing, extra, stale, or changed selections fail closed before the no-op broker is authorized. One monotonic 18-second budget covers the request body, both target scans, every inventory subprocess, and the broker commit; expiry returns HTTP 408 and cannot create a session or advance its sequence. This stays below the Desk 20-second abort, the readiness probe's 22-second curl limit, and the handler's 30-second last-resort cutoff.
