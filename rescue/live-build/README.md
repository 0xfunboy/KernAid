# Rescue image

This Debian 13 (`trixie`) live-build profile creates an amd64 hybrid ISO for legacy BIOS and UEFI. It starts XFCE and opens the local KernAid Desk web bundle in Chromium app mode. Host storage automount is denied for the live user. Each QEMU smoke test attaches a disposable target disk and byte-hashes it before and after boot to prove zero target writes.

Before SHA-256 is calculated, the build finalizes the immutable Phase 0 device layout declared in `rescue/image-layout/device-layout.v1.json`. It writes only MBR slot 3: type `0x83`, start LBA `33554432` (16 GiB), and `16777216` sectors (8 GiB). The ISO file is not padded or enlarged. Consequently the entry intentionally points beyond ISO EOF and describes where a `KERNAID_VAULT` can exist only after the ISO is written to media of at least 24 GiB; the supported capacity claim is 32 GB or larger. The release ISO itself never contains a formatted vault, a key, or provisioning code.

Debian isohybrid images have one narrowly allowed MBR overlap: bootable slot 1 type `0x00` is an image envelope that contains slot 2 type `0xEF`, the EFI System Partition. The finalizer accepts only that exact containment form; it rejects every other slot 1/2 overlap or ordering, any occupied slot 4, any conflicting slot 3, an ISO reaching the reserved vault start, and non-regular image files. Re-running finalization is idempotent only when slot 3 already contains the exact layout-v1 bytes. The QEMU smoke script runs the same verifier read-only before boot.

Build the feature-gated vault binaries first with `cargo build --locked --release -p kernaid-rescue-secrets --features experimental-vault-manager --bin kernaid-rescue-vaultd --bin kernaid-rescue-vaultctl`, then build the keyless provider boundary with `cargo build --locked --release -p kernaid-rescue-openai-executor --bin kernaid-rescue-openai-executor`. Build the image in a disposable Debian environment with `sudo just build-rescue`. The build stages only those three amd64 ELF files, installs both daemons under `/usr/lib/kernaid` and the companion under `/usr/bin` as root-owned mode 0755, and removes the temporary source-tree staging copies on exit. Before live-build runs, a bounded descriptor-based `readelf` gate rejects any unexpected interpreter, runtime search path, or shared-library dependency. The GitHub `rescue` workflow tests the executor, performs both build phases, waits for the existing general and validated-target-selection serial markers in QEMU BIOS and UEFI, verifies zero target writes, and uploads the ISO, SHA-256 checksum, QEMU logs, and derived catalog entry.

The image starts `kernaid-rescue-vaultd.service` at boot together with its mode-0660 root:`kernaid-vault` `SOCK_SEQPACKET` socket. The service uses systemd notification only after daemon initialization, a private mount namespace, a preserved mode-0700 runtime directory, and a delegated pids cgroup with a `supervisor` subgroup. The unit admits only the bootstrap set `CAP_SYS_ADMIN|CAP_KILL|CAP_SETPCAP`: before READY the worker drops to exact `CAP_SYS_ADMIN`, then the supervisor drops `CAP_SETPCAP` and attests exact `CAP_SYS_ADMIN|CAP_KILL` across every task. `CAP_KILL` is used only with the exact `SO_PEERPIDFD` registered from an authenticated Agent connection; no authenticated-peer `SO_PEERCRED` numeric PID is converted to a pidfd. `RestrictSUIDSGID` is intentionally absent: systemd 257 implements it by denying every `openat2` call, while the daemon requires descriptor-bound `openat2` resolution for its path-security boundary. `NoNewPrivileges`, the capability bounding set, strict filesystem protection, root-only runtime ownership, and the remaining sandbox gates stay enforced. The daemon crosses only systemd's known `RuntimeDirectory` bind-mount boundary from a validated `/run` descriptor, then requires the opened directory and its named entry to be the same root-owned mode-0700 object on `/run`'s tmpfs; every child lookup restores beneath/no-symlink/no-magiclink/no-cross-mount resolution. The daemon explicitly enables and reads back the delegated `pids` controller before it creates the sibling worker cgroup, then requires exact recursive sibling/leaf topology. On a marker-free boot, any capability, pidfd, cgroup, worker-startup, Probe, or health-check failure exits without notification; only a marker that existed before startup may notify as contained status-only `PersistentFault`. The live user remains exact UID 1000 and receives Debian live-config's complete default group set plus `kernaid-vault`; the UI remains a separate `DynamicUser` and never receives vault secrets. Readiness fails closed if that account binding, the empty kernel core filename, inactive swap, or subordinate-ID policy is not present. The image also masks `swap.target`, disables systemd fstab/GPT swap generation with `systemd.swap=0`, disables core storage globally, and keeps `LimitCORE=0` as defense in depth.

The image also enables a mode-0660 root:`kernaid-provider-client` sequential-packet socket. Desk's `DynamicUser` receives the provider-client group alongside its existing `kernaid-inspect` group, never `kernaid-vault`. `Accept=yes` starts one `kernaid-openai` nologin/no-home process for one packet; systemd allocates its UID instead of pinning a collision-prone number, and the vault daemon resolves and validates that UID from its already validated `/etc/passwd` descriptor before minting the Agent role. The Agent can request only `vault.status`, `provider.status`, and one leased `provider.openai.borrow`; Codex, audit/report, configure, and logout remain unavailable. Each borrow registers the accepted socket plus direct peer pidfd before worker dispatch, transfers one exact-size/EOF private pipe, and releases only after full socket HUP, pidfd exit, and supervisor output finalization. Lock, stop, fault, or lease expiry kills only that pidfd and waits all three factors before locking or disarming.

The executor retains a private network namespace, `AF_UNIX`, empty capabilities, strict read-only filesystem/device/kernel policy, `TasksMax=1`, a 145-second outer bound, zero core limit, null output streams, and control-group teardown. It performs only the fixed audited `api.openai.com:443` TLS/SNI/Host plus `POST /v1/responses` exchange, with compiled roots and no destination, trust, model, tool, command, or environment override. Its local AF_UNIX stream reaches a non-template, `Accept=no` `systemd-socket-proxyd` running as the distinct secret-blind `kernaid-openai-egress` account without vault/provider groups or capabilities. The proxy's immutable destination is `api.openai.com:443`; on systemd 257 `--connections-max=1` may admit two connections because of its pre-insertion count check, so the unit sizes three tasks and resources for two and does not treat that limit as a credential boundary. These static and unit gates do not by themselves constitute physical OpenAI qualification.

The lifecycle smoke has a separate QEMU-only credential bridge. The host passes the exact, repository-pinned `tools/build-rescue/provider-lease-probe.py` bytes through the system-manager credential fw_cfg namespace; neither that helper nor any test credential is staged into the ISO, squashfs, or image manifest. Ordinary boots have neither credential copy and start none of the six non-enabled probe units. An opted-in boot requires byte-identical raw-fw_cfg and manager copies with exact root-owned, non-writable metadata before readiness creates a distinct root-only validation marker and synchronously starts the three bounded trigger sockets. One DynamicUser probe with only `kernaid-provider-client` access exercises `Status` through the shipping executor without vault or egress access. A separate exact `kernaid-openai` Agent validates an OpenAI key-pipe lease without reading its bytes, first through normal exit and then while held. The held path can reach only a root-owned fixed kill socket; its instantiated service additionally requires the daemon's real lifecycle marker before issuing one literal `systemctl kill --signal=KILL --kill-whom=main` operation. All helper output is a fixed boolean marker, and malformed, partial, stale, or unpinned credentials fail Rescue readiness.

The workflow keeps two intentionally separate boot attestations. The original `qemu-smoke.sh` boots the ISO as a virtual CD-ROM once per firmware and remains the evidence consumed by catalog v1. The additional root-only `qemu-usb-smoke.sh` copies that finalized ISO, without truncation, into the prefix of one sparse 32,000,000,000-byte raw medium under `/tmp`. It binds only p3 through a newly allocated offset/size-limited loop, provisions it as LUKS2 plus ext4 with the exact `KERNAID_VAULT` labels, creates the root-owned V1 marker/layout, and invokes the separately built host probe to create `DeviceIdentity` and initialize the encrypted journal with its canonical identity-binding event. Its random key and wrong-key fixture are mode 0600 files beneath `/dev/shm`; neither they, the provisioner, nor the probe are added to the ISO.

After the initialize lifecycle closes cleanly, the loop is detached and the same raw medium boots twice through QEMU `usb-storage` for each firmware. UEFI receives a fresh OVMF VARS copy on each boot, while the disposable observation target remains a separate writable virtio disk. Prefix, provisioned p3, and target hashes are checked after each boot and across the complete two-boot window. Only after that raw-byte window closes does the host reattach the exact p3 slice, prove wrong-key rejection without residue, and run the probe in verify mode. The verify mode authenticates the journal-to-identity binding and loads the same device identity; LUKS and filesystem UUIDs must also remain stable. Both successful managed lifecycles must shut down without a mount or mapper, and the final loop must be detached.

Each USB log therefore contains exactly one `KERNAID_QEMU_USB_ATTESTATION_V1` line and one catalog-v2-compatible `KERNAID_QEMU_USB_VAULT_ATTESTATION_V1` line. `p3_before_sha256` and `p3_after_sha256` describe the post-initialize raw bytes across the two QEMU boots. The later read-write ext4 verify mount is deliberately outside that hash window and receives its own `KERNAID_QEMU_USB_VAULT_RAW_SCOPE_V1` digest, because an ordinary clean ext4 mount may update filesystem metadata. CI feeds both firmware logs to the inactive catalog-v2 entry generator as a contract check; this does not add an image to the trusted catalog.

This evidence proves boot survival of host-initialized encrypted state on disposable QEMU media and requires the packaged daemon to reach notified readiness after its read-only startup probe. It does **not** prove that the live guest unlocks or otherwise mutates p3, and it does not itself exercise the companion passphrase flow, unlock/lock transitions, crash recovery, or in-guest secure-state lifecycle. Those read-write claims are gated separately by `qemu-vault-lifecycle-smoke.sh`; they deliberately remain outside the byte-inert catalog evidence described here.

The generated image is an engineering preview. An MBR partition entry beyond the end of the ISO is deliberate but unconventional and remains an engineering gate for ISO tooling and physical USB firmware. Secure Boot, Wi-Fi coverage, physical-machine compatibility, real-account OpenAI TLS and production credential/provider operation on real hardware remain release gates.

The loopback Rescue API exposes `GET /api/rescue/installed-targets`, `POST /api/rescue/select-installed-target`, and `POST /api/rescue/inspect-installed-target`. Desk drives them as an explicit scan → select → read-only inspect sequence; inspection accepts exactly the selected `scanFingerprint` and `targetId`. Identifiers use a random root-only key created in `/run` for the current boot, so separate one-shot helper instances share one identity epoch and every reboot invalidates it. Each operation re-scans before accepting an identifier, and a completed inspection re-scans again after cleanup. The scan collector runs one fixed, bounded `lsblk` metadata command, returns only normalized topology and boot-ephemeral identifiers, and excludes mounted/live-image disks. Repeated or incoherent kernel `MAJ:MIN` identities and shared/N:M topology make every involved disk non-selectable.

Desk accepts an inspection only when its exact schema, read-only/no-replay policy, claims, OS family, source reference, scan fingerprint, and target identifier remain cross-bound to the current selection. It then creates one SessionDriver evidence record containing only the bounded normalized Linux or Windows corpus, its versioned collector identity, and a fixed corpus-derived summary. Rescue-runtime inventory is used only for the visible live-environment status and the opaque session target fingerprint; it is never mixed into the installed-system diagnostic corpus. The deterministic provider requires that single corpus record and rejects duplicate, mixed, legacy selection-only, wrongly scoped, wrongly typed, or non-canonical evidence. Refresh, retarget, stale asynchronous responses, identity mismatch, and failed diagnosis revalidation invalidate the prepared inspection/session; target-identity failures also invalidate scan and selection. A performed mount without verified cleanup blocks further inspection until Rescue is restarted. Typed encrypted, Apple-filesystem, complex-storage, and unsupported-filesystem results remain explicit unsupported outcomes and never trigger unlock or activation.

The HTTP/UI process remains a `DynamicUser` with `NoNewPrivileges` and no mount capability. It can send only a fixed operation plus the two opaque identifiers over a mode-0660 Unix socket owned by the dedicated `kernaid-inspect` group. `Accept=yes` creates one root service instance, cgroup, and private mount/network namespace for each connection. Each instance has a 20-second systemd runtime limit, a two-second stop limit, `KillMode=control-group`, and handles exactly one frame before exiting; the kernel still cannot guarantee prompt termination of a task stuck in uninterruptible D-state, so hostile-filesystem kernel hangs remain an explicit physical/VM test gate. The helper resolves the exact kernel device itself, opens one direct devtmpfs block node read-only with no symlink following, verifies `st_rdev`, and mounts `/proc/self/fd/N`; neither an HTTP caller nor the UI can provide a command, device path, filesystem, mount option, or content path. When Windows has one qualified sibling ESP, the helper repeats that descriptor-bound process serially only after the NTFS mount has been removed and verified.

Offline inspection v1 allows only a leaf ext4 filesystem or a leaf NTFS filesystem directly on a disk. ext4 uses kernel flags `ro,nodev,nosuid,noexec,nosymfollow` plus `noload`. The kernel `ntfs3` driver does not implement `norecover`: KernAid mounts it exclusively with those read-only kernel flags, no filesystem-specific option, and never `force`; mount verification rejects a reported `force` super-option. On an `MS_RDONLY` ntfs3 mount the driver does not apply log replay, but KernAid does not classify or validate the volume's clean, dirty, hibernated, or scheduled-check state. The result therefore labels NTFS volume state `unqualified` and returns only static presence markers as `observed-untrusted`.

For a direct Windows partition on GPT, the resolver additionally accepts only exactly one direct sibling with the standard EFI System Partition GUID, leaf `part` topology, an unmounted `fat`/`vfat` signature, and a complete normalized identity that remains identical across every re-scan. Disks with any mounted descendant are excluded from target selection. For an otherwise-selectable Windows target, the helper mounts the qualified sibling as `vfat` with the same read-only kernel flags and no mount data, then checks only `EFI/Microsoft/Boot/bootmgfw.efi`, `EFI/Microsoft/Boot/BCD`, and `EFI/BOOT/BOOTX64.EFI`. The public corpus returns their presence as three booleans only when inspection and cleanup both succeed. Zero siblings, multiple siblings, or an otherwise-unqualified sibling produce the typed states `not-present`, `ambiguous`, or `unsupported` with all three facts `null`; no device identity, path, directory listing, or file content crosses IPC.

The helper never follows fstab, executes or chroots into target content, launches a mount helper, removes a hibernation file, unlocks encryption, or activates storage. LUKS, BitLocker, APFS/HFS, LVM, mdraid, Btrfs, XFS, F2FS, nested mappings, conflicting OS hints, and ambiguous device identities return typed fail-closed errors. Content reads use a static path allowlist, directory file descriptors, `O_NOFOLLOW`, regular-file checks, incremental directory caps, and byte/file/response/deadline limits. Results contain a bounded normalized Linux or Windows corpus classified as `observed-untrusted`; raw registry hives, machine IDs, fstab sources, account names, device identifiers, commands, paths, stdout, and stderr are not returned.

Success is reported only after a normal (never forced or lazy) unmount, mount-table postcondition, unchanged open-device identity, and an identical post-cleanup target resolution. Every response is followed by one-shot service/cgroup exit, so a cleanup failure cannot reuse that mount namespace. Claims distinguish mount attempted/performed/cleaned, content inspected, and installation confirmed; they always state that auto-unlock, mutation, diagnosis, and repair were not performed. This is filesystem evidence capture, not a diagnosis or repair handler.

The BIOS and UEFI QEMU smoke path opts in explicitly through a QEMU-only fw_cfg marker, so ordinary Rescue boots never auto-inspect a customer target. It inspects a deterministic ext4 installed-Linux fixture marked `needs_recovery`, one raw GPT Windows disk containing both a seeded FAT ESP and NTFS installation partition, and one whole-disk NTFS clone altered by `ntfsfix`. The guest must select the GPT Windows partition through normalized public topology, report the ESP as `inspected`, and return all three seeded EFI markers. The altered whole-disk case must remain explicitly `not-present` with null ESP facts. Both NTFS filesystems must be accepted by the shipping kernel's ntfs3 driver exclusively read-only without `force`; their volume state remains explicitly unqualified. The smoke path byte-hashes all three complete raw images before and after the complete boot, so the GPT digest covers both sibling partitions and the partition table. Readiness requires normalized static corpora, exact no-replay/no-force policies, verified cleanup, and identical raw hashes. If that kernel rejects either NTFS fixture or skips the sibling ESP inspection, image qualification fails instead of weakening the policy or overstating support. Physical-machine coverage remains a release gate.

Rescue Observe authorization requires the existing request fields plus exactly `"rescueTarget":{"scanFingerprint":"…","targetId":"…"}`. The server performs selection A, runtime inventory, then selection B; both complete selection responses must be identical. Its `targetFingerprint` is SHA-256 over the UTF-8, NUL-delimited sequence `kernaid-rescue-observe-target-v1`, runtime inventory fingerprint, scan fingerprint, target ID, and the complete candidate encoded as JSON with recursively lexical keys, ASCII escaping, and no whitespace. Missing, extra, stale, or changed selections fail closed before the no-op broker is authorized. One monotonic 18-second budget covers the request body, both target scans, every inventory subprocess, and the broker commit; expiry returns HTTP 408 and cannot create a session or advance its sequence. This stays below the Desk 20-second abort, the readiness probe's 22-second curl limit, and the handler's 30-second last-resort cutoff.
